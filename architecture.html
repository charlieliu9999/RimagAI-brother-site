MCOS：医疗 AI 的
智能·认知底座

当模型能力逐渐成为基础资源，医疗行业真正缺失的不是更多 AI 工具，而是一层能够把模型、数据、流程、治理与进化组织起来的智能·认知底座。

阅读白皮书全文 →

核心判断

医疗 AI 的主要矛盾，正在从"模型能力不足"转向"架构能力缺位"。单点 AI、传统 CDSS、工作站插件和通用 Agent 编排框架都能解决部分问题，但很难同时回答场景感知、上下文组织、分层推理、执行控制、治理约束与持续进化这些系统级问题。

MCOS 不是 HIS/EMR/PACS 本身，也不是某个医疗大模型的别名，而是把多种能力组织进临床工作流的系统层。

六层架构

L1-L4 构成前向运行链路，L5 横切治理，L6 负责持续进化

L1

感知层 Perception

多模态信号采集与预处理——文本、影像、语音、行为、结构化事件。让系统"看见"临床现场。

已验证
L2

上下文层 Context

患者纵向上下文、当前 encounter 上下文、场景工作流上下文。把离散信息组织成语境，而不是堆叠 token。

已验证
L3

认知层 Cognition

意图识别、推理、规划、工具调用。分层推理、显式不确定性、场景化认知模式。知道何时给建议，何时提示需要人工确认。

已验证
L4

执行层 Execution

建议、草稿、预填、受控写回——按风险等级分级执行。核心不是"自动化越多越好"，而是"在正确边界内安全落地"。

已验证
L5

治理层 Governance

横切所有层级的约束框架：权限分级、日志与审计链、风险控制与中断机制、责任归属。没有 L5，MCOS 只是能力系统；有了 L5，才是可落地的临床辅助系统。

建设中
L6

进化层 Evolution

经验萃取、反馈学习、技能优化。让系统不停留于部署时的静态能力水平，而在实际使用中持续改进。

技术实现

RimagAi Brother 对 MCOS L1-L4 的工程级验证

🔀 双通道 AI 架构

  • OpenClaw 远程通道：Agent 编排、多模型、记忆、检索
  • Local Agent 本地通道：AgentCore + LLMClient + ToolRegistry
  • StreamRouter 按配置自动选择，不做 fallback
  • 三层归一化配置：ModelProfile → PromptTemplate → AgentBlueprint

🔌 MCP 协议 + Skill 化

  • Model Context Protocol 可扩展工具框架
  • 支持 stdio / SSE / HTTP 三种传输
  • Skill 成为 MCP 工具说明书：mcpServerId + toolWhitelist
  • promptFragment 自动注入系统提示词

⚙️ 规则引擎

  • 5 种规则类型：模式替换、正则、阈值、必填、术语冲突
  • 3 个内置规则集：报告质控、病历质量、费用合规
  • 本地优先，零延迟同步执行
  • 完整 CRUD UI + 实时预览

🏥 院内系统集成

  • HIS API 客户端：患者摘要、时间线、检验、影像
  • MySQL 连接池：Schema 获取 + 安全参数化查询
  • FunASR 语音识别：WebSocket 流式 2pass/online
  • DICOM 医学影像查看与分析

验证状态

诚实说明当前进展与未完成部分

当前阶段

RimagAi Brother 已在 7 个核心临床场景中，对 MCOS 前四层（L1-L4）的若干关键能力完成工程级验证，包含 58 个测试用例。可以审慎地说，高价值场景与前四层逻辑已获得初步支撑。

但不能说 MCOS 已完成平台化、合规化和临床终局价值验证。L5 治理层和 L6 进化层仍处于建设早期或目标态推演阶段。白皮书中的效率与延迟数据，应被视为工程验证阶段的参考值，而不是医院真实生产环境下的系统性临床结论。
